# Spec: a note as a Word file (DOCX)

**IS NOW** = true of the code today (⚠ = known defect) · **SHOULD BE** = agreed target.
Format: [ADR-0001](../decisions/0001-spec-driven-development.md). Issue: #487.

A note is exported as a Word file (`.docx`) through pandoc, the reverse of the Word import
(IMP-035 to IMP-046): docx → note → docx keeps as much as the import kept. pandoc is the user's
program (BUILD-018), found as the import finds it (IMP-036). Shale prepares the note's text
(DOCX-003), pandoc reads it with commonmark and a Lua filter of Shale's (DOCX-004 to DOCX-006),
writes the docx with a reference document (DOCX-007, DOCX-008), and Shale finishes what pandoc's
docx writer cannot say (DOCX-009). Tests are named `file.rs::test_fn` (under `src/`).

What the import already lost cannot come back: merged table cells (they come back as empty
cells), figure and table numbers (Word fields), tab stops, line spacing set on single paragraphs,
small caps, the page setup of all but the last section. A note made in Shale has no original:
its look comes from its `print-*` properties (DOCX-008).

| ID | Rule | Status | Code | Test |
|---|---|---|---|---|
| DOCX-001 | **Export to Word** (#487). A note's ⋯ menu and the context menu of a note in the file tree have the entry **Export to Word…** below *Export to PDF…* (not for drawings, other files or folders). It opens a dialog: *Save as* (a path field, `<vault>/exports/<note name>.docx`), the box **Use the original Word file as the template** (shown only when the note's `source:` property is a link to a `.docx` file of the vault that exists, DOCX-007; ticked), the box **Table of contents** (ticked as the PDF dialog's box would be for the note: `ExportOptions::with_note_properties`, PDF-008, PDF-013), the box **Open the file afterwards**, and *Export* and *Cancel*. A line says where pandoc was found, or, without pandoc, "pandoc was not found (Settings → Import)" and *Export* is disabled. The export does not need the Word import setting (IMP-036) to be on. | SHOULD BE | `docx_export/dialog.rs`, `layout.rs`, `panels.rs`, `app/docx_export.rs` | |
| DOCX-002 | **The run** (#487). *Export* starts a background job (JOB-001) and the dialog shows that it works; closing the dialog cancels it. pandoc is run with an argument list, no shell, stdin closed, no console window on Windows (as the import, `pdf/tex/proc.rs`), in a private temporary folder outside the vault that is removed afterwards, and killed after 120 s: `pandoc note.md -f commonmark+pipe_tables+strikeout+footnotes+tex_math_dollars+wikilinks_title_after_pipe+autolink_bare_uris+task_lists -t docx --lua-filter=<filter> --resource-path=<vault folder> --reference-doc=<reference> -o out.docx`, with `--toc --toc-depth=3` when the box *Table of contents* is ticked. The filter (`assets/export/shale-docx-export.lua`) is built into the program and written to that folder. Only when pandoc ends with success and the file is finished (DOCX-009) is it written, atomically, at the path of the dialog (its folder made when missing); the vault is scanned again, the dialog closes, a toast names the file, and it is opened with the system's program when the box says so. A failure writes nothing and the dialog says why (pandoc's first error line). The text exported is the note as the window has it (unsaved typing included). | SHOULD BE | `docx_export/mod.rs` (`export`, `args`), `app/docx_export.rs` | |
| DOCX-003 | **The text pandoc reads** (#487). The front matter is taken off. Every embed `![[target]]` (with `#…` and `\|…` after the target or not) whose target the vault resolves from the note (`Vault::resolve`, LINK-*) is written with the vault path of its file instead of the target (`![[z_media/a b.png\|300]]`), so pandoc finds it below the vault folder (`--resource-path`); an embed that does not resolve and anything in fenced code or inline code is left as it is. | SHOULD BE | `docx_export/mod.rs` (`prepare_text`) | |
| DOCX-004 | **Formatting back to Word** (#487). The filter turns Shale's Markdown back into Word formatting: `==text==` and `<mark>` without a colour and with `background: #FFFF00` are Word's yellow highlight; `<span style="color: #RRGGBB;">` is a text colour and `<mark style="background: #RRGGBB;">` another background, each written as a character style with the colours (DOCX-009) named `Shale colour RRGGBB`, `Shale colour RRGGBB on RRGGBB` or `Shale on RRGGBB` (a run has one style, so a colour inside a background, or the other way round, is one style of both), and bold, italic and the other formatting inside them stay; `<u>` underline, `<sub>` and `<sup>` sub and superscript, `<s>` and `~~…~~` strike-through; `<br>` and a new line inside a paragraph are a line break (IMP-037 writes Word's line breaks as new lines); a tag without its end is left out. A link `[[note]]` or `[[note\|words]]` is its words (the note's name without `.md`, `#` as ` > `), as it has no place in the Word file. Footnotes, tables (pipe tables), lists, tasks, quotes, code, math (`$…$`, `$$…$$`, Word's equations) and web links are pandoc's own. | SHOULD BE | `assets/export/shale-docx-export.lua` (`inlines`, `marks`, `tags`, `wikilink`) | |
| DOCX-005 | **Pictures and captions** (#487). An embed of a picture (png, jpg, jpeg, gif, bmp, tif, tiff, svg, emf, wmf, any case) is a picture in Word; its width is the share of the text width it has in the editor (`\|360` is half of the 720-point column, PDF-005, at most the whole width), without a width it keeps its own size; words after `\|` that are no size are its alternative text. Any other embed (a note, a PDF, a sound, a drawing) is its file name in italics. A paragraph that holds only a picture, followed by a paragraph that is all italic (what the import makes of a Word caption, IMP-037), becomes a picture with that caption (pandoc's *Captioned Figure* and *Image Caption*), and the caption is the picture's alternative text too. | SHOULD BE | `assets/export/shale-docx-export.lua` (`embed`, `caption`, `blocks`) | |
| DOCX-006 | **Page breaks, alignment and the title** (#487). A page-break marker (PDF-020) is a page break. The paragraphs and headings in an alignment wrapper (PDF-028) are centred, flush right, justified or left (`w:jc` `center`, `right`, `both`, `left`, set by DOCX-009 from a mark the filter puts in each); an opening line without its closing line aligns nothing, and the wrapper lines are never text. The title block the import writes (IMP-042, IMP-046): a centred wrapper as the first thing of the note holding a `#` heading and at most an italic paragraph below it, becomes Word's *Title* and *Subtitle*, not a heading. | SHOULD BE | `assets/export/shale-docx-export.lua` (`blocks`, `title`, `page_break`) | |
| DOCX-007 | **The original as the template** (#487). With the box ticked (DOCX-001) the reference document is a copy of the original Word file, so its styles, fonts, numbering, headers and footers come back. pandoc adds none of its own styles when the reference is a real Word file, so Shale first merges into the copy's `word/styles.xml` every style of pandoc's default reference (`pandoc --print-default-data-file reference.docx`) whose id and name (case ignored) the original lacks: *Body Text* without its paragraph spacing (the body keeps the original's Normal), and a `w:basedOn`, `w:next` or `w:link` that names a style of pandoc's is renamed to the id of the original's style with the same name (a German Word file calls Normal `Standard`). Without the box, or without an original, the reference is made from the note (DOCX-008). | SHOULD BE | `docx_export/reference.rs` (`merge_styles`, `from_original`) | |
| DOCX-008 | **The template from the note's print settings** (#487). Without an original the reference document is pandoc's default with the note's `print-*` properties (PDF-013, read as the PDF export reads them, a bad value ignored) laid into `word/styles.xml`: `print-font` (`serif` Times New Roman, `sans` Calibri, `mono` Courier New) for the defaults and every style that names a theme font, `print-font-size` (the defaults' `w:sz`), `print-line-spacing` (`w:line` = factor × 240, `auto`), `print-paragraph-spacing` (`w:after` = pt × 20 in the defaults; *Body Text* loses its own spacing), `print-align: justify` (Normal `w:jc both`, the headings `left`), `print-heading-color` (Heading 1 to 9 and Title), `print-heading-weight` (bold or not), `print-heading-sizes` (Heading 1 to 6) and `print-break-before` (`w:pageBreakBefore` for the headings up to that level). A note without these properties gets pandoc's default look. The Word import of such a file gives the same properties back. | SHOULD BE | `docx_export/reference.rs` (`from_props`) | |
| DOCX-009 | **Finishing the file** (#487). After pandoc, Shale changes the docx: a paragraph with the filter's mark (DOCX-006) gets its `w:jc` (in the order of the schema, an old one replaced) and the mark goes; a character style `Shale colour …` / `Shale on …` gets `w:color` and a `w:shd` fill; the last `w:sectPr` of the body gets the page of `print-paper` (`w:pgSz`, landscape when wider than tall) and `print-margins` (`w:pgMar`, keeping its header, footer and gutter distances) when the note has them, because pandoc takes the page of the first section of a reference with several; a picture in `word/media/` that no relationship names is left out (pandoc copies the reference's media). The parts are packed again, compressed (deflate), `[Content_Types].xml` first. A file that cannot be finished is an error of the export. | SHOULD BE | `docx_export/finish.rs` (`finish`) | |
| DOCX-010 | **Word export tests** (#487). The fixtures of the import (`src/testdata/docx/`, IMP-039) are imported with the real pandoc, exported again and read back by pandoc as plain text: the words of `styled`, `picture` and `tables` all come back, of `text` at least 95 % (small caps and the definition list are lost at import); `styled` comes back with its colours, highlights, page breaks, Title, Subtitle and Letter paper. The text preparation, the merging and generating of styles and the finishing are tested without pandoc; the tests that run pandoc skip with a printed note without it (BUILD-018). `scripts/roundtrip-docx.sh <file.docx>` (a developer tool, DEV-004) does the round trip for any Word file and prints the share of words that came back. | SHOULD BE | `docx_export/tests.rs`, `scripts/roundtrip-docx.sh` | |
