## How drawings work (no Excalidraw code inside)

Drawings are **not** the Excalidraw web app. There is no browser view, no JavaScript, no downloaded binary and no Excalidraw source code in this project. `src/drawing.rs` is a small drawing editor written from scratch in Rust and drawn with egui, like the rest of the app. It shares only the **file format** with Excalidraw: it reads and writes the open `.excalidraw` JSON scene format (`type: "excalidraw"`, `version: 2`, an `elements` list with fields such as `strokeColor`, `roughness`, `points`, `seed`).

- **Reading and writing**: `serde` structs for the scene and its elements. Fields this editor doesn't know about are kept as they are and written back, so a file made on excalidraw.com survives a round trip.
- **Drawing**: shapes become point outlines. The "sketchy" look is a seeded wobble with a double stroke, plus hatch and cross-hatch fills computed by clipping parallel lines to the shape. The seed comes from the element's `seed`, so the look doesn't flicker. This is a lookalike of the hand-drawn style, not a port of the rough.js library.
- **Editor**: tools (hand, select, rectangle, diamond, ellipse, arrow, line, pen, text, eraser), selection and resize, a style panel, undo and redo, pan and zoom, a dark canvas.
- **Code layout**: `src/drawing.rs` (file format, rendering, editor core), `src/drawing_connect.rs` (labels, connections, line endings, style panel, arrange buttons; a child module so it can use the editor's internals), `src/drawing_layout.rs` (pure geometry: anchors, crossing count, auto layout, spread), `src/drawing_links.rs` (links in drawings, read-only view).
- **In notes**: `![[Sketch.excalidraw]]` renders the same shapes as a thumbnail in the reading view.
- **Pictures**: `src/drawing_pictures.rs` finds the picture of each `image` element (the plugin's `## Embedded Files` section, read into `Scene::embedded`, or a `dataURL` in the scene's `files`) and loads it as a texture for painting or as an image for the PDF.
- **Links in the index**: `Vault::drawings` holds the links of every drawing and canvas (`drawing::link_lines`: one line per element text or `link` field with a link), next to the notes; backlinks, the graph, rename and move use both. Rename and move rewrite drawings with `drawing::rewrite_link_texts` in the file's own format, never canvases.
- **Not covered yet**: frames, groups, elbow (right-angled) arrows, labels on arrows, rotation handles, export to PNG/SVG. The Obsidian plugin's `.excalidraw.md` files are read and written by `src/excalidraw_md.rs`. Obsidian canvases (`.canvas`) are converted to a scene by `src/canvas.rs` and only shown read-only (or converted into a new `.excalidraw.md`); Shale never writes a canvas. Unknown element types are drawn as a dashed box and kept in the file unchanged.

Dependencies of the whole app are only `eframe`/egui (window and UI), `serde`/`serde_json` (files), `dirs` (config and cache folders), `image` (pictures and screenshots) and `libc` on Unix (local date).

German/English stop words, words of 4+ letters, numbers left out. Learned in a background thread when the vault changed (at most every 2 minutes), saved to `<vault>/.shale/tag-words.json` and loaded when the vault opens. Deterministic (sorted, same input → same output).

## Platforms (raba/shale#53)

- Linux, macOS and Windows are supported (BUILD-005). The system-specific code is small and sits in
  few places, each with a `cfg` and a test: `fsutil.rs` (no-replace rename: `renameat2` / `renamex_np` /
  `MoveFileExW`, DATA-013; locks through `File::try_lock`; owner-only files, DATA-014), `secret.rs`
  (`mlock` / `VirtualLock`, hardening, SEC-023), `opener.rs` (`xdg-open` / `open` / `ShellExecuteW`,
  SEC-022), `cal_time.rs` (local zone, CAL-018), `gitsync.rs` (computer name), `secrets.rs` (keyring: `secret-tool`,
  Keychain, Credential Manager, SEC-003, SEC-024, SEC-025) and the Wayland-only drop code (`wl_drop.rs`, `tb_store.rs`,
  `import/from_programs.rs`, IMP-011).
- `windows-sys` (only for Windows, also for the Credential Manager) and `security-framework` (only for macOS, the Keychain) are the extra dependencies; everything else is `libc` (Unix) or std.
- Tests that need what only one system has (Unix permission bits, a `/bin/sh` stand-in for GnuPG, a
  Secret Service, Wayland, the podman stacks) are `cfg`-gated or print `skipping: …`.
- `cargo xwin clippy --target x86_64-pc-windows-msvc --all-targets` checks the Windows code from Linux
  (needs `cargo-xwin`); macOS code is only checked by the GitHub job (the C parts of `ring` and SQLite
  need the macOS SDK).
- `.gitattributes` forces LF in the working tree, so Windows checkouts match the byte-exact tests.

## Needs work / known issues

- **Drag and drop from Thunderbird**: the first real try showed an empty file list (Thunderbird through X11 creates the file only for file managers); now handled through Thunderbird's local copy, but not yet tried with a real Thunderbird. On Wayland it depends on what Thunderbird hands over: if it offers the message file (or the whole message), the import works directly; if it only offers a link into its own folders, the dialog explains to drag the message to a folder first or use "Save As…". The toast / dialog names the kinds that were offered, which tells which case it is. Dragging events out of Thunderbird's calendar works if it offers calendar data (`text/calendar`) or an .ics file.
- On X11, the window toolkit only reports dropped files (no position, so the folder used last is preselected, and no data drops like whole messages or calendar data).

- If picker keys still misbehave on a desktop, turn on the key recorder, repeat the problem once and read the log: it shows exactly which events arrive and what state the picker was in. Picker keys are now handled both before and after the text box. If a desktop's input method still delivers keys some other way, use the `--keys` aid with `SHALE_DEBUG=1` to see what arrives.
- Inline images are positioned from the link's start on its row. An image link sharing a line with other text makes that whole row tall.

- The editor recomputes colouring for the whole note on each change. This is fine for normal notes, but very large files (more than about 1 MB) may feel slow.
- The task list and status bar rescan all tasks every frame. They should be cached by `vault.generation` for big vaults.
- Rename is offered for folders too, but link rewriting is only done for single notes and drawings.
- Hover tooltips on links appear after egui's normal tooltip delay.
- The colour and layout are an original dark theme that aims for the general feel the person described. No pictures of the original app were available to compare against.

## Development notes

- **No warnings policy**: `cargo build`, `cargo build --all-targets` (tests) and `cargo build --release` all build with **zero warnings**, including a from-scratch rebuild of the vendored crates in `vendor/`. Keep it that way. Check with `cargo build --all-targets 2>&1 | grep '^warning'` before finishing any change. Deprecated egui calls use the replacement egui suggests (`Id::unique`, `Ui::scope_id`, `TextEdit::align`). Code that only tests use is marked `#[cfg(test)]`, and unused code is deleted.

- Normal build: `cargo build`. `.cargo/config.toml` points the linker at `.toolshim/cc`. That small helper hands linking to the system `cc`/`gcc`/`clang` when one exists, and otherwise (in sandboxes without a C toolchain) links with Rust's bundled lld and the startup objects in `.toolshim/`. It is not part of the app itself.
- To capture views for review: `shale --screenshot shots/x.png --view tasks`.
